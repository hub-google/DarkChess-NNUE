# 台灣暗棋自我進化系統

以 GitHub Actions 持續產生完整合法的自我對弈棋譜，將資料保存在 Hugging Face 資料集，持續訓練研究神經網路模型，並透過新舊模型公平對戰決定是否升級正式冠軍。

[開啟暗棋網站](https://hub-google.github.io/DarkChess-NNUE/)｜[查看執行紀錄](https://github.com/hub-google/DarkChess-NNUE/actions)

**產生大量棋譜或通過程式測試，不代表棋力提高。** 新模型必須通過配對棋力驗證，才可以取代現有模型；目前仍無世界頂尖棋力的獨立證明。

## 一、目前的唯一正式架構

| 工作流程 | 程式檔 | 職責 |
| --- | --- | --- |
| 自動對弈與中斷接續 | .github/workflows/self_play.yml | 自我對弈、搜尋進度接續、當輪集中上傳與 HF 回讀驗證 |
| 模型訓練與升級 | .github/workflows/train.yml | 程式回歸測試、棋譜整併、模型訓練、公平對戰驗證及升級 |
| 暗棋網站部署 | .github/workflows/deploy_pages.yml | 網頁測試、建置及發布 |

系統運作順序：

1. 使用現任模型產生棋譜；只有完整且合法的對局能成為訓練資料。
2. 每個 GitHub Run 啟動十五個獨立 CPU 運算員，並行自我對弈五小時，之後由第十六號運算員統一驗證、去重、打包並上傳私人資料集；上傳結束後此 Run 結束並啟動新 Run。
3. 整併原始棋譜、產生訓練局面、重新分析關鍵局面，優先從 `models/research.nnue` 接續訓練；首輪研究權重不存在時才從 `models/champion.nnue` 啟動。
4. 訓練成功且權重通過完整性驗證後，將候選權重保存成 `models/research.nnue`，**與已完成訓練的棋譜快照一起提交到 GitHub**；此步不等待 SPRT，也不修改冠軍。
5. 使用相同底牌、首翻條件及雙方交換模型身分的配對對戰評估研究模型和冠軍。
6. 只有統計驗證明確接受新模型更強時才晉升 `models/champion.nnue`，並更新網站；其餘情形保留正式冠軍，但研究模型下一輪仍繼續學習。

## 二、共用搜尋引擎與完整思考

**網站、自我對弈與模型升級驗證都呼叫同一個 DarkChessEngine 類別**，位於 frontend/src/engine/search.ts，避免分成互相矛盾的兩套下棋邏輯。

- 網站入口：frontend/src/engine/search.worker.ts，於背景執行搜尋，並顯示實際完成深度、節點數及耗時。
- 正式對弈入口：src/workers/self_play_shared.ts，**第 1～10 手都完整搜尋一層；第 11 手起使用單人試跑驗證的六層或八層完整搜尋**。
- 模型驗證入口：src/workers/sprt_shared.ts，以雙方一致的驗證運算條件比較新舊模型。
- 評估器：frontend/src/engine/nnue-core.ts，依公開盤面特徵估計局面價值；不能偷看尚未翻開的真實棋種。

**正式自我對弈不設每步秒數或節點數上限。** 第一手同樣執行完整一層公開資訊搜尋並記錄真實節點數、估值和深度。若最佳首翻位置估值相同，從同分最佳位置中隨機選取以保持多樣性。每手都必須完成當手指定層數才允許落子。

GitHub 單次運算工作仍受約六小時的平台期限限制。每個對弈運算員在執行期限前保存已完成的棋步、根分支及可安全重用的精確子局面結果；後續工作透過檢查點接續。檢查點保存在執行成品中的 resume_state/*.json 與 *.memo。還沒完成的最深層子分支可能需要重算；**進度接續不等於能任意中斷每一條程式指令，也不保證有限時間內一定能算完十二層**。

2026-10-27 的 8 層單人試跑在第 11 手長時間搜尋後被取消，未產生完整棋譜。依使用者指示，正式深度暫採 6 層並啟動 15 名 CPU 運算員，實際效能與模型棋力仍待驗證；單人試跑並未證明 6 層能在指定時間內完成整局。若深度 6 仍無法完成，需再優化搜尋而非偽造成功棋局。搜尋仍需完整算完指定深度；每手記錄真實深度與運算量，未完成棋局不得訓練。短時間程式測試使用 SELF_PLAY_SMOKE_DEPTH=2，**正式運作不可設定這個測試專用變數**。

## 三、暗棋遊戲規則

- **棋盤與棋子**：四列、八行，共三十二格；紅方帥一、仕二、相二、俥二、傌二、炮二、兵五；黑方將一、士二、象二、車二、馬二、包二、卒五。
- **開始與分配陣營**：全部面朝下；先手玩家第一次翻開的棋子顏色，決定先手的陣營。
- **合法行動**：翻開暗子、移動己方明子至上下左右相鄰空格、或依吃子規則取代敵方明子。
- **一般吃子階級**：帥將、仕士、相象、俥車、傌馬、炮包、兵卒依階級壓制；同階可互吃。兵卒可吃將帥，將帥不可吃兵卒。
- **炮包跳吃**：必須和目標同行或同列，恰好隔著一個炮台，炮台可為任何明暗棋子，且能跳吃任何階級敵子。
- **終局**：一方沒有可用棋子或輪到行動卻沒有合法行動，依規則判勝負；連續六十個半回合未翻牌、未吃子判和。
- **禁止長追**：不允許同一追擊關係在逃跑路線上重複繞圈；追擊者必須變步，沒有合法變步時依法判負。

實際合法走法以 frontend/src/engine/board.ts 和獨立的 Python 重播裁判及其測試為準。修改棋規時必須同步修改雙方及回歸測試。

## 四、棋譜來源、格式與安全

公開資料集：hub-google/DarkChess-NNUE-Data（上傳需授權）。

| 儲存位置 | 用途 |
| --- | --- |
| staging/ | 第十六號上傳員集中存入的完整對弈批次 |
| replay_buffer.jsonl.gz | 原始棋譜的可重建事實來源，依唯一棋局識別碼去重 |
| training_cache/ | 從原始棋譜產生的可重建二進位訓練快取 |
| GitHub 執行成品 | 完成棋譜與尚未完成的搜尋檢查點 |

每局包含：id、ver、model（棋局與模型版本）、hid（裁判私有底牌）、mov（完整動作）、q（搜尋估值）、v（神經網路估值）、qd（每步完成深度）、qn（每步節點數）、qt（每步耗時）、pi（候選行動教師機率）、res（紅方視角勝負）、draw_reason（和局原因）、ply（步數），以及紅黑雙方模型識別碼。

**搜尋器不得使用 hid 偷看暗牌**；只能從公開盤面與剩餘棋種數量推算翻牌機率。未完成棋局不是和局，不能寫入訓練資料。只有合法終局、依每手規則完成指定搜尋深度（第一手也實際完成一層）、可由裁判重播驗證的棋譜，才可以上傳。

資料整併以固定時間快照為範圍；合併後必須下載核對，且只有已成功驗證的暫存批次才能刪除。HF 上傳失敗、驗證失敗或網路中斷時，不能刪掉唯一的原始資料與可恢復檢查點。

原始棋譜不因難例重新分析而改寫。訓練時可混合高估值分歧局面與一般隨機局面，從而避免只學少數特殊情況。

## 五、訓練、模型與棋力驗證

- src/training/consolidate_buffer.py：整併及去重原始資料。
- src/training/build_training_cache.py：取樣棋局、建立訓練快取、分析難局面。
- src/training/train.py：以 CPU 訓練估值模型，研究線從最新 `models/research.nnue` 接續（沒有研究模型時才由冠軍起步）。
- src/training/research_checkpoint.py：保存研究權重前驗證模型架構、權重有限值與推論輸出；不允許壞模型被當成有效續訓成果。
- src/workers/sprt_shared.ts：以**同一套共用搜尋引擎**讓候選與現任模型公平對戰。
- src/training/export_nnue.py：將通過驗證的現任模型匯出給網站。

估值模型大致為公開盤面 498 特徵、256 與 32 個隱藏節點、單一估值輸出。訓練支援左右鏡射、上下鏡射、旋轉與紅黑互換等資料增強。

另有實驗性走法預測模型，但**目前不能宣稱該模型已融入正式搜尋樹或有獨立證實的棋力貢獻**。

模型對戰採相同隱藏底牌及首翻條件，並交換雙方使用的新舊模型，以抵銷部分暗棋翻牌運氣。只有統計檢定結果明確為 ACCEPT_H1 才晉升現任模型；失敗、證據不足或對戰異常都不能升級。模型驗證採雙方對等的運算上限，**與正式自我對弈使用單人試跑驗證深度的要求不同**。

研究線和正式冠軍互相獨立：研究線持續繼承已完成訓練的權重；**SPRT 未通過不會抹掉研究成果，亦不會直接改寫正式冠軍**。棋譜快照標記必須與研究權重在同一個 Git 提交中更新，避免資料標記已前進但模型沒有保存。研究模型正常訓練不代表棋力更強，只有冠軍晉升需要統計驗證。

資料太少應繼續累積，不可產生假的候選模型或訓練成功紀錄。實際最低局數、訓練輪數與驗證門檻須以目前工作流程及程式設定為準。

## 六、連續執行、資料恢復與取消操作

每個 Run 只執行一次 15 人矩陣自我對弈，各人計算 18,000 秒（五小時），完成後由第十六號統一上傳 HF，最後派送新的獨立 Run，並結束當前 Run。每個 CPU Job 預留額外時間處理 artifacts，以避開六小時的單 Job 限制。

- 下個 Run 接續同編號運算員在前一個 Run 的檢查點，兼容歷史五輪的 artifacts；只有合法完整的棋譜交給 HF 上傳，未完成搜尋只保留檢查點。
- 每小時檢查是否有正在執行的對弈；只有上一輪正常成功且目前無執行工作時才補啟動新輪次。若上一輪失敗或取消，必須保留狀態且不自動跳過失敗。
- 使用者按取消後，系統不得自行派送被取消工作的後續輪次。
- 每輪由第十六號運算員直接上傳、讀回校驗 SHA-256；若發生上傳或驗證錯誤，該輪標記失敗，不啟動下一輪，亦不會由每三小時排程事後補傳。另有每日訓練及每月排程保活。
- 沒有新的**完整有效棋譜**時，只有確認十五個運算員皆已保存搜尋檢查點，才能接續下一個 Run；不宣稱 HF 上傳成功，也不因此觸發模型訓練。少了棋譜且少了檢查點則標記失敗。
- 網站顯示的局數是最後一次已發布統計，不是即時、不經驗證的原始爬取數字。

資料接續、訓練、驗證與部署都會受到 GitHub、HF、網路及額度限制；排程存在不代表永不中斷，也不代表每輪必定產出更多棋局。

## 七、檔案地圖與測試

| 位置 | 職責 |
| --- | --- |
| frontend/src/engine/board.ts | 網頁棋規與終局判定 |
| frontend/src/engine/search.ts | 唯一正式搜尋決策核心 |
| frontend/src/engine/nnue-core.ts | 共用估值運算 |
| frontend/src/engine/search.worker.ts | 網頁背景搜尋 |
| src/workers/self_play_shared.ts | 自我對弈、已驗證深度與中斷接續 |
| src/workers/sprt_shared.ts | 新舊模型配對驗證 |
| src/workers/upload_batch.py | 集中上傳與驗證棋譜 |
| src/training/ | 棋譜處理、獨立裁判、訓練、模型匯出 |
| test/ | 搜尋、棋規、資料安全與工作流程契約測試 |

本地回歸驗證：

~~~bash
python -m pip install -r requirements.txt
python -m unittest discover -s test -p "test_*.py" -v
npm ci --prefix frontend
npm test --prefix frontend -- --run
npm run build --prefix frontend
./frontend/node_modules/.bin/tsc -p src/workers/tsconfig.selfplay.json
~~~

僅限功能驗證的短局測試：

~~~bash
BATCH_SIZE=1 NUM_BATCHES=1 SELF_PLAY_SMOKE_DEPTH=2 node .shared-build/src/workers/self_play_shared.js
python src/training/validate_replay.py --directory output_data --min-games 1
~~~

**驗收必須分開確認**：程式測試成功、棋譜合法、HF 回讀成功、候選模型確實訓練、棋力統計足以晉升、網站模型成功更新。不能把一個綠燈當成全部完成。

本 README 是目前唯一的正式專案說明。舊的 docs/requirement、已退休工作流程紀錄與歷史架構已移除，不再讓互相矛盾的舊版規格誤導維護者。
