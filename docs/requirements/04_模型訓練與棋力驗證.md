# 04. 模型訓練與棋力驗證

本文件區分「已實作」、「實驗性功能」及「尚未啟用的 roadmap」，避免誇大棋力與自動化狀態。2026-10-22 新增 CPU 有界搜尋、教師機率棋譜與實驗性獨立 Policy Head。

## 一、 目前已實作的持續進化閉環

現行流程為：

1. **Self-play**：以目前 champion 為主，並可抽樣近期 archive champion 當對手，產生 replay。
2. **Replay consolidation**：將 cutoff 前 staging 對局融合進最多 500,000 局的 raw replay buffer。
3. **Binary cache + reanalysis**：將 raw replay 轉成可重建的 `training_cache/*.npz`，並用目前 champion 對少量 hard positions 重新深搜。
4. **Training**：從 champion 權重續訓，產生 `models/challenger.nnue`。
5. **Paired SPRT**：challenger 與 champion 進行同底盤、模型換邊的成對驗證。
6. **Promotion**：只有 SPRT 回傳 `ACCEPT_H1` 才能晉升；其餘情況保留舊 champion。
7. **Archive**：晉升前的 champion 會放入 `models/archive/`，保留近期版本供 self-play 對手池使用。

目前 `self_play.yml` 與 `train.yml` 的 cron 都已依使用者要求註解，因此上述生產流程 **不會自動定時執行**；兩者目前只保留 `workflow_dispatch` 手動啟動。CI、pipeline smoke 與 benchmark 則仍可依各自 workflow 的 push 條件自動驗證程式變更。

## 二、 訓練資料與 Target

raw replay 每步可保存：

- `q`：該步被選動作的 chance-search 根值。
- `v`：搜尋前 NNUE 靜態值。
- `res`：最終紅方視角勝負。

一般有完整深度搜尋結果 `q` 的盤面使用：

`Target = (1 - Q_TARGET_WEIGHT) * res + Q_TARGET_WEIGHT * q`

預設 `Q_TARGET_WEIGHT=0.5`，可以實驗 0、0.25、0.5 等比例。若沒有 `q`，或 `qd=0`（因計算預算耗盡的 heuristic fallback），則只能用最終勝負 `res`；不能將 fallback 評估當成深搜答案。Hard-position 排名也必須忽略 `qd=0`。

### Hard-position reanalysis

`build_training_cache.py` 會先利用舊 `|q-v|` 與 deterministic random sampling 建立候選，再以目前 champion 評估候選盤面，優先重算 `|q_old-v_new|` 大的盤面。重新深搜得到的 `q_new` 只寫進 `reanalysis_overrides.npz`，不會修改 raw replay。

### 搜尋教師與獨立 Policy Head（實驗性）

- Self-play 於每步保存已完成搜尋深度 `qd`，以及經側方視角轉換後、前 16 個動作的 softmax `pi`。
- `build_training_cache.py` 在驗證棋譜合法且真實終局後，把 `pi` 寫入 binary NPZ；`qd=0` 不會成為 Policy 標籤。
- `policy_train.py` 用 CPU 訓練獨立的 `498 → 64 → 1024` Policy 網路，輸出 `models/challenger.policy`；若沒有教師資料就略過。
- 模型驗證通過才能連同 Value NNUE 一起晉升 `models/champion.policy`。Self-play 可以載入已晉升 Policy，預設以 15% 權重與搜尋機率混合（僅探索步、僅合法動作），避免一味跟自己的最佳走法重複對弈。
- `pipeline_smoke.yml` 會用新 `challenger.policy` 再完成一局 Policy 引導的真正對弈與終局驗證。
- Policy **尚未直接參與正式搜尋的節點展開／SPRT**，因此不可宣稱已完成 AlphaGo Zero 的完整 Policy-Value 搜尋閉環。
- 後續應以相同 CPU 時間評測 Policy 帶來的 move ordering / exploration 改善，通過外部基準後才接入正式引擎。

## 三、 目前訓練超參數

`train.yml` 目前使用固定、安全且可由環境變數覆寫的參數：

- Optimizer：AdamW
- 預設 Learning Rate：`1e-4`
- Weight Decay：`1e-4`
- Batch Size：`1024`
- Training Epochs：`3`
- 最大 training samples：`2,000,000`
- 對稱增強：預設開啟
- 紅黑互換增強：預設開啟

若沒有任何訓練資料，或整輪訓練沒有產生有效 batch，流程必須直接失敗，禁止產生可晉升的 challenger。

## 四、 資料增強

4x8 棋盤支援以下幾何等價變換：

- 原盤
- 左右鏡射
- 上下鏡射
- 180 度旋轉

這些變換在訓練時即時套用，不需把同一局 replay 複製四份到 Hugging Face。

另可做紅黑互換；紅黑互換時會同步反轉 value target 的符號。

## 五、 Paired SPRT Champion Gate

暗棋存在翻牌隨機性，因此驗證採 **paired match** 而不是單純比較一批獨立勝率。

每一組 pair：

- 使用相同的隱藏底盤。
- 使用相同首翻條件。
- Game A 與 Game B 交換 champion / challenger 的模型身分。

目前 `train.yml` 呼叫：

- 最多 400 pairs
- search depth = 8
- node budget = 20,000
- `elo0 = -15`
- `elo1 = 15`

只有驗證 step 明確設定 `passed=true` 時才執行 promotion。H0、未達界線、驗證失敗都不會覆蓋現有 champion。

## 六、 CPU-only 搜尋與效能驗證

專案目前不依賴 GPU / CUDA。CI 安裝 CPU-only PyTorch，正式 self-play、training、SPRT、benchmark 都必須能在 GitHub-hosted CPU runner 上執行。

搜尋採：

- Star1-style chance-node bounds
- iterative deepening
- 依盤面階段配置 node budget
- fully hidden opening 使用較淺搜尋
- self-play 每步 `SEARCH_MAX_SECONDS` 預設 3 秒，且使用有界 node budget；若 depth-1 尚未完成即耗盡預算，只能返回 `depth=0` 的公開盤面合法 heuristic fallback，禁止取消預算重搜。正式預設節點額度 early=500、mid=1200、late=2500，需以完整棋局測試調高。
- NNUE full-forward / incremental hybrid evaluator
- 無暗子的小型殘局可使用 exact tablebase

`benchmark.yml` 會對固定 early / mid / late positions 與完整低預算對局測量 throughput，避免只靠主觀判斷宣稱優化有效。

## 七、 尚未啟用的 Roadmap

下列概念可保留作後續研究方向，但 **目前沒有自動 state machine 在 production workflow 中執行**：

- 依「連續 SPRT 失敗次數」自動調整 learning rate。
- 依和局率自動切換 Fast / Plateau / Refinement 狀態。
- 自動改變 replay window 容量。
- 自動改變 SPRT Elo bounds。
- 因停滯而自動提高 self-play 搜尋深度或 exploration temperature。

若未來要啟用，應先把狀態持久化、切換條件、上限／下限與回歸測試實作完成，再更新本文件為「已實作」。
