# 03. 訓練資料與分散式儲存

本文件以目前 `master` 的實作為準。訓練資料由 **GitHub Actions CPU Runner** 產生，集中存放於 Hugging Face Dataset `hub-google/DarkChess-NNUE-Data`；瀏覽器前端目前不負責產生正式訓練資料。

## 一、 分散式 Self-play 與寫入隔離

目前 `.github/workflows/self_play.yml` 的矩陣固定為 **15 個 Worker（worker_id 1~15）**。每個 Worker 在自己的 GitHub-hosted CPU runner 上執行 `src/workers/self_play.py`，再由 `src/workers/upload_batch.py` 將已完成對局打包後上傳。

- 寫入位置：`staging/worker_${WORKER_ID}/`
- 每個 Worker 各自寫入 staging 子目錄，避免檔名碰撞與並行覆寫。
- 上傳前先把本地完成的散檔合成單一 `batch_*.jsonl.gz`，減少 API 次數與 Hugging Face 檔案數。
- 目前自動 cron 已依使用者要求註解，**只保留 `workflow_dispatch` 手動觸發**。
- 歷史版本曾使用 worker 16~20，因此清理／融合程式仍會掃描 1~20，目的是清掉舊資料，不代表現在會啟動 20 台 runner。

## 二、 Raw Replay 是唯一原始事實來源

Hugging Face 上的 `replay_buffer.jsonl.gz` 是可重建訓練資料的 **raw replay source of truth**。

`src/training/consolidate_buffer.py` 會：

1. 依 cutoff 固定本次要納入的 staging 快照。
2. 合併舊 `replay_buffer.jsonl.gz` 與 cutoff 前的完整新批次。
3. 以 immutable game `id` 去重。
4. 保留最新最多 **500,000 局**，並受最大壓縮檔容量限制保護。
5. 上傳新 buffer 後重新下載驗證筆數、排序與去重。
6. 驗證成功後，只刪除這次已納入的 staging 檔；cutoff 後或並行上傳的新資料保留至下一輪。

這使 self-play 與 training 可以併行，而不會因 train 清理 staging 把新對局誤刪。

## 三、 單筆 Replay 格式

目前正式版本為 `v2.1.x`，現行產生器使用 `v2.1.0-perpetual-chase`。

```json
{
  "id": "uuid-string",
  "ts": 1785471174900,
  "ver": "v2.1.0-perpetual-chase",
  "model": "sha256-model-id",
  "red_model": "sha256-model-id",
  "black_model": "sha256-model-id",
  "hid": [0, 1, 1, 8, 9],
  "mov": [105, 332, 12, 881],
  "q": [0.02, -0.15, -0.08, 0.31],
  "v": [0.01, -0.09, -0.12, 0.28],
  "res": 1.0,
  "ply": 45
}
```

欄位意義：

- `mov`：完整動作序列的整數編碼。
- `q`：該步被選動作的根搜尋值。
- `v`：搜尋前 NNUE 靜態評估值。
- `res`：最終結果，固定紅方視角（1=紅勝、-1=黑勝、0=和）。
- `red_model` / `black_model`：該局兩邊實際使用的模型內容 ID，讓舊棋譜可追溯到產生它的模型世代。
- `hid`：只供裁判／重播決定實際翻牌結果。

### Imperfect-information 硬限制

搜尋不得讀取未翻暗子的真實 `hid` / `hidden_pieces` 內容。搜尋只能使用公開盤面與由已翻棋子推導出的 `remaining_counts` belief state。測試會刻意建立「公開狀態相同、私有底牌排列不同」的盤面，確認搜尋結果不會改變。

## 四、 Raw Replay 與 Binary Training Cache 分離

訓練不直接在每個 epoch 反覆解析 gzip JSON。流程會先執行 `src/training/build_training_cache.py`：

1. 讀取 raw replay。
2. 每局挑選有限數量盤面。
3. 立即轉為 NNUE feature tensor。
4. 寫成 `training_cache/cache_*.npz` shard。
5. 產生 `training_cache/manifest.json`。
6. 產生 `training_cache/reanalysis_overrides.npz`。

`training_cache/` 是 **可重建的衍生資料**，不取代 raw replay，也不需要回寫 Hugging Face。這樣可降低反覆 JSON/gzip 解碼成本，又保留完整重建能力。

## 五、 Hard-position Sampling 與 Reanalysis

每個候選盤面會利用 `|q-v|` 衡量「搜尋與 NNUE 靜態值的分歧」。

建 cache 時同時保留：

- 高 `|q-v|` 的 hard positions。
- deterministic random 候選，避免只學極端盤面。

若 `models/champion.nnue` 存在，會再用目前 champion 對候選盤面重新評估：

1. 先計算新模型 `v_new`。
2. 依 `|q_old-v_new|` 排序。
3. 對最值得重算的少量盤面重新跑 `ChanceSearch`。
4. 將新的 `q_new` 與 target 寫入 `reanalysis_overrides.npz`。
5. 訓練資料集讀 cache 時，以 override 覆蓋舊 target。

**Raw replay 永遠不被 reanalysis 改寫。**

## 六、 模型世代追蹤

Self-play 的模型 ID 由模型檔內容產生，因此同一份權重即使檔名不同仍會得到相同 ID。每局 replay 保存 `model`、`red_model`、`black_model`；binary cache 也保存每筆樣本的 `source_model`，可追查樣本來自哪一代模型。

## 七、 前端與訓練引擎的角色

- **Python**：目前正式 self-play、chance search、NNUE 訓練、reanalysis、SPRT 與 tablebase 的真實執行端。
- **TypeScript / Frontend**：網頁對弈、顯示與部署；目前不作為正式分散式訓練資料 worker。

兩邊若共享規則邏輯，仍需用測試確保規則一致，但正式訓練資料的來源以 Python pipeline 為準。
