# 03. 訓練資料與分散式儲存

原先單機版的訓練計畫無法滿足高強度的算力需求，轉型為**分散式志願運算架構 (Distributed Volunteer Computing)**。

## 一、 20 台機器併發寫入的災難避免
若 20 台機器同時向 Google Drive 或關聯式資料庫寫入盤面資料，必定會遭遇以下問題：
*   **API Rate Limit (頻率限制)**：瞬間高頻寫入會直接被拒絕請求（HTTP 429）。
*   **Race Condition 與 DB Lock (鎖死)**：關聯式資料庫同時 Insert 巨量資料會導致嚴重的 I/O 卡頓。
*   **單點故障與網路延遲**：單步/單局即時傳送會浪費大量時間在建立 TCP 連線，效率極低。

## 二、 最佳儲存架構與資料格式 (批次封裝 + Replay Buffer 自動融合)
為了達到 **完全不卡住、零衝突、最高效能、且避免超過 Git/HuggingFace 檔案數量限制**，採用「暫存隔離 + 定期自動融合 (Replay Buffer)」架構。
*   **資料儲存庫連結**：所有的訓練資料將會被自動上傳與融合成單一檔案至 Hugging Face Dataset 儲存庫：[hub-google/DarkChess-NNUE-Data](https://huggingface.co/datasets/hub-google/DarkChess-NNUE-Data)
*   **Worker 暫存隔離 (Staging Zone)**：20 台 Worker 併發執行自我對弈時，將資料寫入 `staging/worker_${WORKER_ID}` 暫存區，避免多 Worker 並行上傳時在根目錄發生檔案碰撞。
*   **Replay Buffer 自動融合 (`consolidate_buffer.py`)**：
    *   在每日台灣時間 03:00 的訓練 Pipeline (`train.yml`) 執行時，自動建立固定時間 cutoff 的資料快照；手動執行則以該 job 實際開始時為 cutoff。
    *   腳本只將檔名上傳時間戳記小於或等於 cutoff 的完整批次，與歷史對局合併為單一高效率壓縮大檔 `replay_buffer.jsonl.gz`。cutoff 之後才完成上傳的批次保留到下次訓練。
    *   **並行安全清理**：self-play 可在 train 執行期間繼續產生及上傳。新 replay buffer 重新下載並完成筆數、去重、排序與容量驗證後，只逐一刪除本次成功納入快照的 staging 檔案，禁止刪除整個 `staging/` 資料夾。任何步驟失敗均保留來源檔案。
    *   **冪等重試**：每局以 immutable `id` 去重；若 replay buffer 已上傳但清理中斷，重跑不會重複加權同一棋局。Hugging Face 並行 commit 發生衝突時，重新讀取最新狀態並只重試仍存在的快照檔案。
    *   **檔案數量與容量控制**：根目錄永遠保持單一 `replay_buffer.jsonl.gz` 大檔案，徹底防止觸發 Hugging Face「單一資料夾最多 10,000 個檔案」的硬性限制，並將訓練時的資料下載連線次數由數萬次減少為 1 次。
    *   **滑動窗口 (Sliding Window)**：融合腳本維護最高 **500,000 局** 的上限，自動淘汰超過容量的舊對局，確保訓練集維持在最新且品質最高的棋局。
*   **斷點防護 (Graceful Shutdown)**：為避免 GitHub Actions 6 小時限制或中斷導致算力浪費，腳本需捕捉 `SIGTERM` 訊號，收到中斷時強制將當前已完成的局數提早打包上傳至暫存區。

## 三、 單筆對局資料結構 (極致整數編碼)
為了最大化中央 Python 訓練腳本的 CPU 讀取效能 (避免大量字串解析)，所有特徵與動作皆須轉為整數陣列 (Integer Encoding)。

```json
{
  "id": "uuid-string",
  "ts": 1785471174900,
  "ver": "v2.0.0-belief-search",
  "model": "champion-498",
  "hid": [0, 1, 1, 8, 9, ...], // 32個未翻開暗子的真實排列 (0~13的整數代碼)
  "mov": [105, 332, 12, 881], // 將完整動作(翻牌/移動/吃子)映射為 0~2048 的單一整數 (move_id)
  "q": [0.02, -0.15, -0.08, 0.31], // 每一步被選動作的搜尋根值，固定為紅方視角
  "res": 1.0, // 固定紅方視角：1.0=紅勝, -1.0=黑勝, 0.0=和局
  "ply": 45
}
```
`hid` 僅供裁判重播實際翻牌結果；搜尋與模型輸入不得直接讀取指定暗格的值，只能使用由已翻棋子推導出的公開 `remaining_counts`。訓練預設只接受 `v2.*`，避免舊版必吃隨機策略污染新模型。
*   **優化效益**：檔案體積縮減 80% 以上，並讓 PyTorch DataLoader 能以極低 CPU 負擔直接將字串陣列轉換為 Numpy/Tensor。

## 四、 棋譜解碼與人類可讀顯示 (Human-Readable Translation)
雖然底層儲存極致壓縮為整數 `move_id`，但為了後續開發除錯、Log 輸出以及前端 UI 的歷史回放功能，系統必須實作嚴格的「解碼翻譯層 (Translation Layer)」。

### 1. 輸出格式規範
當需要將訓練資料或對戰紀錄輸出給人類觀看時，必須依賴 `hid` (初始暗子) 與內部盤面狀態推演機，將 `move_id` 轉換為以下清晰易懂的字串格式，嚴格遵守 `[棋子] [起點X,Y] > [終點X,Y] [動作結果]` 的結構：

*   **吃子 (Eat)**：`[主動棋子] [起點X,Y] > [終點X,Y] [主動棋子]吃[被吃棋子]`
    *   範例：`象 8,3 > 7,2 象吃俥`
*   **移動 (Move)**：`[主動棋子] [起點X,Y] > [終點X,Y] [主動棋子]移動`
    *   範例：`卒 1,2 > 1,3 卒移動`
*   **翻牌 (Flip)**：`翻 [座標X,Y] > 出現 [顏色][棋子]`
    *   範例：`翻 8,3 > 出現 紅俥`

### 2. 解碼實作要求
*   所有負責 UI 顯示 (如 `05_前端網頁與容錯機制.md` 所述) 或後端除錯的模組，都必須呼叫標準的解碼函式並遵守此輸出規範。
*   核心引擎與儲存層維持絕對的高效整數運算，**僅在「最後一哩路 (顯示層)」**才進行字串的轉換拼接。

## 五、 核心引擎實作與分離 (Engine Implementation)
系統將維護兩套邏輯等價但針對不同環境最佳化的核心引擎：
*   **後端與訓練端 (Training Node)**：統一使用 **Python + Numba (@njit)** 實作。藉由 JIT 編譯將 Bitboard 與搜尋邏輯轉為底層機器碼，確保訓練腳本 (PyTorch) 呼叫時達到 C 語言等級效能，作為 SPRT 驗證與模型推論的唯一真理。
*   **網頁前端 (Web Client)**：使用 **TypeScript** 實作。專門為了編譯為瀏覽器執行的 Web Worker 而生，負責在志願者的瀏覽器背景高速生成自我對弈資料。開發時必須建立嚴格的測試測項 (Test Cases)，確保 TS 版本的合法步生成與 Python 版本的行為 100% 一致。
